## 1. What I understand about the project

TMT is a small byte-level recurrent language model, not an LLM in the usual tokenizer/context-window sense. Its defining ideas are:

- byte input and byte output;
- a JEPA-style latent prediction objective;
- recurrent trace units (RTUs) with persistent state;
- eligibility/ring credit for delayed embedding gradients;
- an exact dense tail-credit EMA for a sparse set of long-lived (“hot”) dimensions;
- streaming/test-time training;
- fixed-size recurrent state, so memory is O(1) with respect to sequence length.

The canonical model is approximately 4.5M parameters:

```text
dim = 512
layers = 16
batch B = 1024
fp32
TF32 disabled
checkpoint ring_k = 18
TMT_TAIL enabled
```

The important distinction is:

```text
TMT currently has a good implementation and ruler,
but not yet a demonstrated long-memory mechanism.
```

The latest live continuation went from `t=64,747` to `t=94,747` on real TinyStories. It had no non-finite losses and showed the following result:

- held-out CE: approximately `1.1741 -> 1.1902` — statistically neutral;
- distribution-shift CE: approximately `1.1425 -> 1.1264` — statistically neutral;
- cross-domain CE: approximately `3.1532 -> 3.4042` — statistically neutral;
- hot dimensions: `57 -> 115`;
- mean half-life: about `1.12 -> 1.14 bytes`.

So more training changed the recurrent structure, but did not prove useful long-term memory. The central scientific question is:

> **Can TMT learn a new domain while retaining old-domain performance, and can that retention be improved through parameter-role-specific learning rates without damaging existing memory?**

## 3. What is not yet known

These are the open questions that the plan must address, in this order:

1. Are decay parameters receiving a useful, consistent gradient signal?
2. Do dimensions with longer half-lives actually move, carry state, contribute to credit, and affect predictions?
3. Does massed training on one domain cause catastrophic forgetting?
4. Does an interleaved control retain old domains better?
5. Can shared-weight and memory-decay learning-rate roles affect the stability/plasticity frontier?
6. Only after those answers: does the model need a timescale spread, learned write/read gates, or multiple RTU slots?

The most important negative constraint is:

> **Do not infer liveness from sigma or half-life alone.**

A dimension with a long half-life can be unused. A short-memory dimension can be highly active and useful.

### Phase 1 — Implement telemetry without changing the model

**Timebox:** 2–3 hours.

Create a small telemetry module, preferably `telemetry.py`, rather than scattering logging logic through the math code. The telemetry must be observation-only during the first run.

#### Required metrics

At a configurable interval, record:

**Shared/trunk groups**

- mean/median gradient magnitude;
- gradient SNR:
  ```text
  ||EMA(gradient)||² / EMA(||gradient||²)
  ```
- actual parameter movement;
- update-to-parameter ratio.

**Decay groups, per layer and per dimension**

- gradient magnitude;
- gradient SNR;
- actual movement of `layer{i}.decay`;
- effective sigma;
- half-life;
- state RMS;
- state activity;
- eligibility/ring-use mass;
- tail membership.

**Global health**

- `t`, bytes seen, B;
- finite loss and CE;
- hot dimension count;
- counts above 4, 8, 16, and 32 bytes half-life;
- state RMS;
- throughput;
- checkpoint digest;
- whether the run crossed a rebase boundary.

#### Implementation rules

- Use fixed-size tensors for every EMA. A dimension with zero gradient still contributes a zero.
- Keep the existing flat parameter layout and custom fused AdamW.
- Do not change the optimizer, precision, ring size, architecture, data order, or checkpoint math in this phase.
- Do not use `.item()` in the training hot path. Synchronize only at the telemetry interval.
- Emit JSONL or CSV plus a compact JSON summary at each save/evaluation point.
- Make telemetry optional and disabled by default for normal training.

#### Required tests

- a zero-gradient group produces `GradSNR=0` without NaNs;
- a constant-direction gradient produces SNR close to 1;
- telemetry has the same shape before and after a tail rebase;
- a short run with telemetry enabled has the same loss/theta/state as a run with telemetry disabled within the existing parity tolerance;
- telemetry output records non-finite loss loudly.

**Exit condition:** a short CPU run and a short GPU run produce valid telemetry without changing the model trajectory.

### Phase 2 — Implement the continual-learning probe

**Timebox:** 1–2 hours.

The probe should be a small, explicit script such as `continual_probe.py`, not a collection of manually edited trainer commands.

#### Experimental question

Does reading one domain continuously damage performance on previously learned domains?

#### Common starting state

All arms must start from the same checkpoint and use:

- identical initialization state;
- `B=1024`;
- identical optimizer settings;
- fixed data seed where applicable;
- identical evaluation bytes;
- no different architecture, batch size, precision, or checkpoint `ring_k`.

#### Arms for the first run

Keep the first experiment small and interpretable:

1. **Interleaved control**
   - alternate or mix the old domain and the new domain;
   - same total bytes as the massed arm.

2. **Massed training**
   - train continuously on one new domain.

Do not run all six learning-rate arms on the 25th unless the telemetry implementation and the two-arm probe are already complete. The first result should answer the forgetting question, not mix it with every optimizer hypothesis.

#### Evaluation points

Evaluate at:

```text
0 bytes
0.5M bytes
1M bytes
2M bytes
4M bytes
```

At B=1024, these correspond to approximately:

```text
0 steps
488 steps
977 steps
1,953 steps
3,906 steps
```

Use a save/evaluation manifest that records the exact checkpoint at every point. Do not compare a checkpoint 1–18 steps after a resume against a continuous arm without accounting for the ring warmup.

#### Metrics at each point

- clean held-out CE for the old domain;
- clean held-out CE for the new domain if available;
- cross-domain CE;
- shift CE;
- hot-dimension count;
- counts above 8B/16B/32B half-life;
- state RMS;
- telemetry summary;
- fixed-prompt outputs recorded as qualitative evidence only.

#### Primary decision

- **Severe forgetting:** old-domain CE rises materially while new-domain CE improves.
- **Mild/no forgetting:** old-domain performance remains within the practical `0.03 CE` bar while new-domain performance improves.
- **Inconclusive:** uncertainty, contamination, or missing evaluations make the result unusable.

Do not call an improvement “memory” solely because a CE improved. Require telemetry or a direct memory-use probe showing that the relevant state is active and used.

**Exit condition:** the probe can be run reproducibly from one checkpoint, and every evaluation point has an identifiable checkpoint.

### Phase 4 — Analyze and make one architecture decision

**Timebox:** 45–60 minutes.

Use this decision tree:

#### Case A — severe forgetting, decay gradients are weak/inconsistent

The likely issue is optimization/role balance. Next experiment: implement an element-wise learning-rate mask and test:

```text
shared-weight multiplier: 1.0, 0.3, 0.1
decay multiplier:           1.0, 0.3, 3.0
```

Start with a global-LR control. Do not add separate Adam beta values yet.

#### Case B — severe forgetting, but decay gradients/movement are healthy

The current decay parameters may be learning but the shared representation may overwrite old domains. Test the shared-weight multiplier first, then inspect whether long-lived dimensions are actually used.

#### Case C — no forgetting, but long memory remains unused

The model may be stable simply because it is not forming useful long memory. Do not call this a success. Before changing architecture, add a direct memory-use test:

- feed a structured prefix;
- insert a long distractor;
- ask for a predictable delayed byte or structural closure;
- compare the prediction with and without the prefix/state carry-over.

#### Case D — long dimensions are active, but CE is worse

This is a meaningful trade-off. Keep the result if the dimensions improve retention or delayed-task performance, but do not claim general model quality from CE alone.

#### Case E — all results are inconclusive

Improve the ruler and telemetry before changing the model:

- add more held-out slices/files;
- add a balanced multi-domain eval set;
- add direct retrieval/copy probes;
- use at least two seeds for a decision that will influence architecture.

## 6. Optional role-specific learning-rate implementation

Only start this after the telemetry and two-arm forgetting probe are complete.

The current optimizer is a custom fused update over one flat parameter vector. The first implementation should be a fixed element-wise multiplier:

```text
effective_lr[p] = base_lr * role_multiplier[p]
```

where:

```text
shared weights: 1.0
layer*.decay:   separate multiplier
```

Keep the existing Adam moments and beta values. This isolates the role-specific learning-rate hypothesis.

Suggested first matrix:

| arm | shared | decay |
|---|---:|---:|
| A | 1.0x | 1.0x |
| B | 0.3x | 1.0x |
| C | 0.1x | 1.0x |
| D | 1.0x | 0.3x |
| E | 1.0x | 3.0x |
| F | 0.3x | 3.0x |

Every arm must log the exact multiplier and the effective learning rates. Do not interpret a CE change without the forgetting and telemetry metrics.
