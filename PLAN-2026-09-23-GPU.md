## 0. Situation

### 0.1 The bottleneck is throughput, and it is worse than the log says

The model digests data at ~890 B/s (PLAN numbers, numba + B=1024 on this i5-8265U).
At that rate the corpus (198 MB wikistories + ~10 MB novels) is "2.7 epochs at
current speed" and Experiment D arms take 5–8 h each. The plain conclusion:

> **route to intelligence = more bytes/sec, and free GPU hours are the how.**

Measured on this box today (`test-model-thing/.venv`, numba 0.67, numpy 2.5.3):

| config | throughput |
|---|---|
| numpy port, B=64, with numba | 9.6 steps/s = **615 B/s** |
| numpy port, B=1024, with numba (the active trainer, checkpoint stores B=1024, ring_k=18) | 1.0 steps/s = **~1000 B/s** |
| numpy port, B=2048 / B=4096, with numba | 1104 / 1019 B/s — **B/s is flat on CPU**: bigger batches buy nothing here, only memory (1.9 / 3.4 GB RSS) |
| numpy port, system python, **no numba** (BLAS one-hot fallback) | **28 B/s** (0.45 steps/s) — keep using `.venv/` |
| torch per-byte port (main_torch.py) on any hardware | ~B=1 ⇒ latency-bound, ≤ ~1 k B/s (not a path) |

The BLAS fallback is the instruction "build a (256, B·K) one-hot selector and let
BLAS do the reduction" — that is ~256× wasted FLOPs per layer per step (docstring's
own wording). It is also the exact shape of the win: **every op in the numpy
`step_batch` is batchable over B, and a GPU does batched scatter/GEMM for free.**

### 0.3 Throughput — MEASURED on a T4 (2026-09-24, supersedes the estimate)

| B | T4 measured | ms/step | note |
|---|---|---|---|
| 1024 | **32,353 B/s** | 31.7 | 31.6 steps/s |
| 2048 | **32,806 B/s** | 62.4 | |
| 4096 | **34,259 B/s** | 119.6 | 33× the CPU baseline (~1,000 B/s) |

The earlier estimate (100–200k B/s) was **too optimistic by ~5×**: the workload
is not GEMM-bound at this model size. Two findings from the first T4 run:
- A per-step tail-membership sync (copying the ring to CPU, ~0.5 GB/step) was
  99% of step time — fixed (12× speedup) by re-evaluating membership on the

not 32,353.** The table above is a *synthetic-checkpoint* micro-benchmark; the
same bench on the live checkpoint gives 23,796 B/s, and end-of-stream flags
cost 0.8% (so EOS is not the cause). Hot dims doubled 57 → 115 during the
leg, and the tail and the wasted hot-column share both grow with that. Use
21.5 kB/s for all planning.

### 0.4 GPU optimization plan (2026-09-24, from the live-leg profile)

Where the 47.6 ms goes, per step, at the live config (B=1024, dim=512, L=16,
K=18, 115 hot dims, 4.48M params):

| component | traffic/step | share |
|---|---|---|
| ring: `w.mul_(dec)` 75.5 MB + `ring_vals` write 37.7 MB + scatter read 37.7 MB + hot-zeroing ~0.53 MB average/layer, per layer × 16 | **~2,420 MB** | **hypothesis; verify with profiler** |
| tail: `E.mul_(sig)` 241 MB + credit read 121 MB | 362 MB | 9% |
| optimizer (8 passes over 4.5M) + layer activations | 814 MB | — |
| matmul | 26.6 GFLOP ≈ 7.6 ms at ~3.5 TFLOPS fp32 | — |

Budget: ~15 ms bandwidth + ~8 ms matmul + **~25 ms unaccounted → 151M fp32
atomics/step from `dembed.index_add_` plus ~300–400 kernel launches.** The
**ring** is the target, not the tail: it carries full `dim`-wide vectors for K
lags, so it scales with `B × K × dim × layers` while the tail scales with
`B × 256 × hot`.

**Phase 0 — measurement harness first (~30 min).** `bench_variants.py`: one
T4 run benches baseline + every candidate variant in one process (CUDA-synced,
peak memory reported), using a fresh model loaded from the same immutable
checkpoint for each variant. Compare loss, theta, gradients, moments, ring,
and tail state. Without it each idea costs a 25-min leg. Every change below
lands behind a flag so baseline and optimized are comparable side by side.

**Phase A — no intended model change (measure; no fixed speed target).**
- **A1. Skip hot columns in the ring.** The code multiplies the full
  `dim`-wide ring and *then* zeroes the hot columns. At the live H=115 this
  is 115/(16×512) = 1.40% of ring dimensions, not 22%; measure the actual
  gain rather than promising a fixed speedup. A cold-only path must accumulate
  into a `(256, D_cold)` temporary and then add to `dembed[:, cold]`.
- **A2. Fuse the `ring_vals` temp.** `torch.mul(w, dlds, out=ring_vals)`
  writes 37.7 MB/layer that `index_add_` reads straight back. Fusing removes
  ~1.2 GB/step.
- **A3. CUDA-graph the step.** Removes launch overhead and, after the
  `float(loss)` host sync is removed/isolated, some synchronization cost.
  Medium risk; measure launch overhead first.

**Phase B — factored decay (float reassociation only; another 1.3–1.5×).**
- **B1. Ring decay factoring — corrected arithmetic; no promised traffic win.**
  The earlier scalar-per-`(b,k)` sketch was invalid because `dec` is a
  dimension-specific `(D,)` vector. A factored implementation must keep
  `(B,K,D)` factors, so it touches the same ring-sized state as `w.mul_` and
  does not support the claimed 1.2 GB/step saving. It is implemented only as a
  versioned candidate for state-space measurements; the default remains the
  legacy path.
- **B2. Tail decay factoring (versioned state required).** Same for `E`, but
  `E` never resets so `c` underflows — renormalize every N=100 steps (120 MB
  per 100 steps ≈ 1.2 MB/step amortized) and fold `c` into the credit einsum.
  The factor must be persisted; current saved E is already decayed and cannot
  be reinterpreted as factored state.

**Phase C — kill the atomics (the ~25 ms gap; uncertain).**
`dembed.index_add_` scatters 9.4M floats/layer into only 256 target rows, so
~36,864 source contributions per target row per layer on average (profile
actual contention; the old 72 figure was not consistent with the current
shapes). Sort the `B*K` row indices by target byte (18k elements, cheap) and
replace atomics with a segmented reduction. This was the original "next
lever"; the traffic analysis ranks it below A/B because the ring's data
movement is the bigger cost.

**Protocol (non-negotiable).**
1. Local CPU gates after every change (`tests/check_parity.py`,
   `check_gradients.py`, `check_trainer.py`) — free, no quota. The CUDA
   profiler must also compare all state tensors, not only theta.
2. One `bench_variants.py` T4 run per batch of changes, never one leg per idea.
3. Phase B/C reassociate floating point and therefore move the trajectory:
   keep the old engine as the reference, run the candidate behind a versioned
   flag, compare state against the old engine, and require the 0.03 CE ruler
   bar before accepting. Factored state must add an algorithm/checkpoint version
   and persist or explicitly migrate its new decay factors.
4. Nothing goes in RESULTS.md without before/after numbers and a parity result.

**Not levers.** B=4096 is only ~6% better per byte (34.3k vs 32.4k) — the
per-step costs scale with B, so it buys nothing. TF32/bf16 breaks the fp32
parity contract. Lowering `K` or capping hot dims *would* cut cost linearly
but are science decisions (they change the approximation), not optimizations.

## 1. The GPU engine: `gpu_port.py` (torch translation of `numpy_port.step_batch`)

**Do NOT use main_torch.py.** It is per-byte (B=1, latency-bound on every
hardware), MLX-optimizer semantics, and saves safetensors. The numpy port is the
canonical batched math the current run uses; the GPU port is a semantics-preserving
translation of exactly that `step_batch`, keeping the **`.npz` checkpoint format**
so every existing tool (`eval_npz.py`, `memory_report.py`, chat path, the PLAN's
ruler) keeps working and the mid-run checkpoint (t=64,747, 57.6 M bytes) carries over.

### 1.1 Op map (numpy → torch), everything fp32 on CUDA

| numpy op | torch op | note |
|---|---|---|
| `embed[c_arr]` (B,dim) | `embedding(weight, c)` | int64 label tensor |
| per-layer fwd: decay·state+x+dummy, LN, W@h, SiLU | `F.layer_norm`, `mm`, `F.silu` | batch = streams, shapes (B, dim) |
| decoder logits, CE, embed-MSE, var-hinge, stop MSE | same, `torch.logsumexp` | match `numpy_port.step_batch` exactly, incl. the masked var-hinge and `/dim` scaling |
| ring `w *= decays[i]`; `w[:, p] = 1.0`; scatter `dembed[rows] += vals` | `w *= d[:,None,None]`; `w[:, p] = 1`; **`index_add_`** on a (B·K → rows) index | `index_add_` does true scatter-add with duplicate indices = `np.add.at`, at GPU speed (no 256× one-hot waste — the numba loop's job, for free). |
| tail EMA `E *= sig`; `credit = einsum("bvh,bh->vh")`; `E[.,c_b,.] += 1` | broadcast mul; `torch.einsum`; `index_add_` | same rhythm `begin_step → credit → add_byte`, lags ≥ 1 exact |
| embedtrace graft + decaytrace bookkeep + decay grad | same tensor math, `.detach()` where numpy uses stop_gradient | see step_batch lines "grafts (post-vgc)" |
| fused flat AdamW (bias-corrected, wd=0.01) | **custom inline elementwise update on the same flat buffers** (NOT `torch.optim.AdamW`) | numpy's update is `th -= lr·(m̂/(√v̂)+wd·th)` applied in place, and it **`sqrt`s v in place every step** (so the next step re-sqrt's the same buffer — a quirk of the live trainer, faithfully reproduced). Porting it literally makes every element's arithmetic identical on any device. Standard AdamW is *not* equivalent; changing to it would fork the trajectory of the live run. Contract: numpy-parity, verified by `tests/check_parity.py`. |

Also preserved: `ring_k` derived the same way from `decay_init` (checkpoint's K
wins at load), `RING_TOL` env, the `TMT_TAIL` on/off switch, and the tail's
`sig**ring_k > HOT_FRAC` test. One deliberate difference: hot-membership
re-evaluation runs on the documented `REBASE_EVERY=500` cadence (numpy
re-checks every step because the check is free on CPU); on GPU a per-step
re-check copied the ring to host (~0.5 GB/step) and was 99% of step time.

### 1.2 Batch size is a learning knob, not a speed knob (do not raise B for throughput)

`step_batch` reads **1 byte from each of B independent streams per step** — it is
NOT "read B bytes of one text, then learn". B only changes the optimizer
statistics: steps/byte = 1/B, gradient noise, and Adam's granularity. The live
checkpoint is B=1024; the model's whole trajectory (and any future A/B arm) is
anchored to that. **On GPU, per-step cost at these sizes is kernel-launch-
dominated, so B=1024 is the production default.** The old 5–10 ms /
100–200 kB/s estimate was superseded by the live-leg measurement
(~21.5–22.1 kB/s); do not use it for planning. Raising B to 4096 changes the
learning dynamics and is a deliberate experiment.
learning dynamics the run was tuned for (4× fewer updates/byte at the same LR) —
that is a *deliberate experiment*, not the production path.

Policy:
- **Default: B=1024 on GPU — byte-for-byte continuity with the live run**, no LR
  rescaling, no behavior risk. One bridge, same seed, same bytes.
- **B>1024 is an A/B arm, never a default** (§4): same `--data-seed`, matched
  bytes, B ∈ {1024, 4096} × LR (B·LR / √B·LR candidates), judged on the ruler's
  3-file SE. If a bigger batch wins the learning question, adopt it then.
- Ring (B, K≈18, 512) ×16 + tail E (B, 256, H) ×16, fp32 at the default:
  B=1024 ⇒ ring 0.5 GB / tail 0.15 GB total; B=4096 ⇒ 2.0 / 0.6 GB (fits T4's
  16 GB either way). Assert the hot-dim memory cap at init (PLAN risk list's
  blowup guard, ported).

Note: `ring_k` is read **from the checkpoint** (live = 18), never re-derived
from `RING_TOL` — the checkpoint is the source of truth (the eval tools already
do this).

## 2. Checkpoint hub: one truth, two platforms, recoverable (not bit-identical)

**Design rule: every push is content-verified and atomic; a pull refuses the
past and refuses to guess.** Checkpoints are ~70 MB at B=256 and ~173 MB at
B=1024 (measured; params+moments+states+tail; states/tail grow with B).
Transport options in order of preference:

1. **HuggingFace Hub repo** (private, free, both platforms have internet,
   `upload_file`/`hf_hub_download` with resume). Primary.
2. Google Drive (Colab native; Kaggle reads public Drive links via `gdown`). Mirror.
3. GitHub Releases as last resort (single-file ≤ 2 GB, no repo bloat).

Protocol:
- Save exactly like today: `.tmp` + `os.replace` (atomic), **tagged** names
  derived from the rolling basename (`armW_t051234.npz`) so two A/B arms in
  one directory never collide or prune each other, keep last-K locally.
- Every push validates content first (readable npz, internal `t` == filename
  `t`) and uploads a `<name>.sha256` sidecar with the digest and the optional
  `$TMT_RUN_ID`; every pull re-validates, checks the sidecar, and checks the
  parameter count against the receiving model. A mislabeled, corrupt, or
  wrong-shape remote file can never become the loaded truth.
- Push after every save; pull-on-boot selects the max `t` and skips if it is
  not strictly newer than local (a stale mirror can never win). An **equal-step
  remote with different bytes is a conflict** — two writers at the same step
  (concurrent arms/platforms) — and the pull **fails loudly** instead of
  guessing; re-tag one arm or pass `force=True` deliberately. There is no
  "last writer wins" inference from the integer `t`.
- Remote retention: the hub keeps everything (an A/B anchor must never vanish
  silently). Prune explicitly and only on request:
  `python checkpoint_hub.py prune-remote --keep 8` (dry run) `--yes` to delete.
- Ledger: `SCHEDULE.md` records each session's hours so the Kaggle 30 h/week cap
  is never blown mid-experiment. Kaggle's hard 12 h stop is handled by
  `save_every` ≈ every 10 min ⇒ last checkpoint ≤ minutes before the kill; the
  Colab session (or the other platform) resumes it.

Optional ~2× checkpoint shrink (mini-AGI §8.6): store Adam m/v in the saved `.npz`
as bf16 (measured non-accumulating error, 0.1% — the moments re-derive every step).
Defer until checkpoints at B=4096 are annoying the sync; fp32 correctness comes first.

## 3. Correctness gate: parity before GPU hours

`tests/check_parity.py` (plus `tests/check_trainer.py` for the trainer/hub
lifecycle) — the **only** gates between "code written" and "quota spent":

1. Same seed, same 30–150 byte-streams (deterministic bytes), same B.
2. Forward/backward through `numpy_port.step_batch` and `gpu_port` (CPU torch
   mode, so this runs on the laptop, no GPU needed to validate).
3. Assert, with the thresholds the code actually enforces:
   - per-step loss / `last_ce` **< 1e-5** relative (measured 2.9e-07);
   - per-param gradients, `theta`, `m` **< 5e-3** relative and `v` < 1e-4
     (measured worst: gradient 3.6e-03 on the embed rows). The embed gradient
     and the eligibility EMA span orders of magnitude, so a pure relative
     bound is meaningless near zero; these thresholds are ~1.4x the measured
     worst, and a real divergence (orders of magnitude) fails loudly. The
     earlier "~1e-4" claim in this section was aspirational and never held for
     the embed gradient — the gate is now the contract.
   - **ring + tail accumulators** too: `ring_b` ids EXACT, `ring_w` and
     `tail_E` < 5e-3 (measured ~9e-07). A tail bug is the most likely silent
     divergence.
   - post-resume `m`, `v`, `theta` and accumulators are gated as well (they
     used to be printed but not asserted).
4. Saved-state npz round trip (torch → npz → compare) must be bit-identical.
   It proves the *saved* state, not continuation identity: `ring_b`/`ring_w`
   are not persisted (see §2), so a resumed model is **recoverable, not
   bit-identical** — its cold-dim embed credit warms from step 1 and the two
   trajectories separate (measured: embed rel err 6.6e-02 at step 1, abs/RMS
   5.5e-05, loss ratio 1.00; tail E restores exactly). `check_parity.py`
   pins that shape explicitly.
   **A/B rule:** never compare a checkpoint taken within `ring_k` (≤18) steps
   of a resume against a continuous arm — that interval is dominated by the
   ring warmup, not by the treatment.
5. Once: CUDA parity on a real GPU against CPU-torch, comparing loss **and**
   theta, every gradient, `m`, `v`, `ring_b`/`ring_w`, tail cols and tail E
   (loss alone does not prove the credit path agrees). CUDA nondeterminism
   makes two GPU runs differ (mini-AGI: ≈0.03 CE is the real-difference bar;
   the PLAN's 3-file SE ruler is the honest comparator). Measured T4 numbers
   live in RESULTS.md.

Local tools status (`.venv/`, already present, nothing to install): **numba 0.67**,
**numpy 2.5.3**, **torch 2.14.0+cpu** — the parity gate runs on this venv today.
(Guard: always use `.venv/bin/python`; system python lacks numba and drops to 28 B/s.)

## 4. What this unlocks in PLAN-2026-09-22 (the week-1 schedule)

Everything below runs on the same 4.5 M-param model; the GPU only kills the
waiting. Order:

| day | work | where | GPU time |
|---|---|---|---|
| 0 | Phase 0 ruler (held-out split, `--data-seed`, tagged saves) — **code, do once, still needed** | laptop | 0 |
| 0 | `gpu_port.py` + bridge + parity gate passing on CPU torch | laptop | 0 |
| 1 | Colab smoke: pull tmt.npz → 10 k steps → push → resume; Kaggle kernel mirror | both | ~0.5 h |
| 1 | Experiment D arm W (wikistories 20 MB) | Kaggle or Colab | ~10 min |
| 1 | Experiment D arm N (novels 20 MB) | other platform | ~10 min |
| 2 | **corpus verdict** (PLAN Phase 1 decision rule) → Phase 2 spread init | laptop code / GPU verify | 0 |
| 2–3 | Phase 3 A/B (spread vs continuation), both arms byte-matched `--data-seed` | both platforms | ~1 h |
| 5+ | **Batch-size A/B (the "is B=4096 bad for learning?" question, answered by measurement):** same bytes, arms {B=1024 × LR} vs {B=4096 × LR, B·LR, √B·LR}; ruler 3-file SE decides whether coarse-batch is fine or a confound | both platforms | ~2 h |
| 3+ | Phase 4 scale: dim 512→768 (≈10 M params — still trivial for GPU), **plus the new lever: corpus v2 2–5 GB** | long backlog across both platforms | rest of the week |

**The new lever (not in the old PLAN, enabled by GPU): data volume.** The model
is byte-level and 4.5 M params; mini-AGI's measured power law (L ∝ D^−0.243 past
warmup) means more *distinct* text lowers loss. Corpus v2 = **a layered mix tuned
to this model's measured walls** (long-memory dims mostly dead; chat = worst
subject at 1.14 nats), not a random web dump. Searched live (HF API, 2026-09-23),
measured sizes + licenses:

| layer | dataset (verified live) | size | license | why it earns its slot |
|---|---|---|---|---|
| **A — memory driver (base)** | `Despina/project_gutenberg` · fiction_books | 2.7 GB text, **6,322 complete novels** | MIT | narrative prose = paragraphs of coherence ⇒ the exact signal that should grow long half-lives (PLAN Phase 1 arm-N hypothesis). Book-contiguous streaming. |
| **B — breadth (general English)** | `HuggingFaceFW/fineweb-edu` · top-`score` slice | 1–2 GB slice (`score` filter; full repo 2 TB) | odc-by | cleanest large-format general text; kills CE breadth without markup soup; plain `text` column → trivial byte feed |
| **C — dialogue (the chat wall)** | `HuggingFaceH4/ultrachat_200k` · slice | ~0.3 GB of 3 GB | MIT | dialogue turn-taking + cross-turn reference — aimed at filler collapse / no-cross-turn-memory; synthetic but clean and large |
| eval-only | `emozilla/pg19` | 7.1 GB | research-only (books) | **never train on it** — free cross-domain generalization number (Victorian novels, out of distribution) |

≈ **4.5 GB distinct text** (A+B+C) ≈ 20× today's corpus; ~1,000 bytes/param at 4.5 M
params — the right order of magnitude; anything more waits for Phase 4 capacity.

**Explicitly rejected (why):** DCLM-baseline (cc-by-4.0, 228 GB) — FineWeb-Edu is the
same genre, cleaner format; RedPajama/The Pile — FineWeb modern-supersedes them;
The Stack / code (gated + license admin) — revisit as layer D after the corpus
verdict; the Gutenberg repo's `synthetic_relations_*` config — synthetic noise;
Books3 and friends — copyright. Wikistories+novels stay frozen as eval / A/B arms
(ruler hygiene).

**Streaming for a byte-level RTU (important, differs from an LLM pipeline):** the
trainer has no tokenizer — bytes in, no chunking by tokens. To keep long-range
structure intact, stage corpus v2 as books/docs **concatenated in order into ~20–
50 MB files**, each file's line-buckets then give every stream long coherent
stretches (contiguous-chunk mode if added, even better for books). Markup stays
minimal; Gutenberg boilerplate (header/footer) stripped by the stage step.

**Fetch model — installed in-session from the internet, never shipped from the
laptop** (faster: both platforms' uplinks + HF CDN beat any local transfer):

- `fetch_corpus.py LAYERS=A,B,C GB=4.5` runs **inside the Colab/Kaggle session**
  and pulls straight from HF Hub (`hf_hub_download` with resume; pyarrow for
  parquet slicing), strips, normalizes, and publishes versioned files under
  `./corpus/current/` (file order is seeded; source row order is preserved).
  The trainer globs `./corpus/current/**/corpus_*` — no dataset shipping,
  no Drive/Kaggle-Dataset upload step.
- **Amount is a knob, anchored to measured speed**: the script takes a GB budget
  (or per-layer toggles) and the trainer prints an ETA from the session's own
  `bench_gpu.py` numbers, so sizing becomes routine — e.g., a 4.5 GB one-epoch
  pass at the measured live rate (about 21.5 kB/s) takes roughly 58 h, so it
  belongs across resumable sessions; at 0.5 GB the same pass takes about
  6.5 h. Use the session's measured rate, not the old 150 kB/s estimate. The "right amount" is decided per
  session from live throughput, exactly as requested; revisit weekly.
- **Cache, don't re-download**: Kaggle can save the staged `./corpus/` as a
  dataset version once, then later sessions mount it locally (instant); Colab
  mirrors it to Drive once. First fetch is the only slow one (~minutes at HF
  CDN speed). Same bytes both platforms: the corpus spec (repo, score filter,
  ordering seed) is pinned in the repo, not ad-hoc.

Also the PLAN-2026-09-22 ordering rule stands: **Experiment D (arm W vs N) runs
first** on the existing corpora, and its verdict decides whether Gutenberg becomes
the base (likely — that is what layer A assumes) or just a diversity add. Corpus

download/stage happens in-session via `fetch_corpus.py` — so prep is code-only,
zero data movement.

Also **pull two mini-AGI §8 transfers into the same window** — both are one-day

needs a GPU to build — only to test at speed.

### 4.1 TPU — 20 h/wk is real, but do not chase it yet

The 20 TPU hours are the weakest fit in this budget, and the honest call is to
leave them idle until Phase 4 scale demands them. Why:

- **Workload shape**: TMT's per-step work is ~500–800 tiny kernels (512×512
  GEMMs at B=1024), a `index_add` scatter, and Python orchestration — exactly
  what GPUs do well and TPUs (throughput machines for huge dense matmuls) do
  poorly. A TPU v3-8 would underutilize against a T4 here, especially at B=1024.
- **Port cost × parity burden**: TPU trains JAX/TF; torch-XLA on Kaggle TPU is
  unofficial and fiddly. `step_batch` is ~150 lines — a JAX port (jit + vmap over
  streams) is doable, but it is a *second* implementation to maintain, and the
  parity gate (§3) must then hold for numpy ≡ torch ≡ JAX. Real ongoing cost for
  speculative hours.
- **When it flips**: if Phase 4 lands (dim 512→768+, corpus 2–5 GB) and GPU quota
  is still the binding constraint *and* the whole loop is proven on CUDA, the
  JAX port is a weekend with a known spec (the torch port *is* the spec).
  Until then: budget the 20 h as reserve, not runway.

## 6. Risks / watch list

- **Batch-size confound in A/B arms**: every arm must state B + LR; a B=4096 arm is a different learning process, never compared to a B=1024 arm across runs without the ruler.
- **CUDA nondeterminism** (mini-AGI: ≈0.03 CE threshold; two GPU runs differ).
  Never A/B across platforms in one arm; always `--data-seed` + fixed seed; judge
  with the 3-file SE ruler, not single runs.
- **TF32 / AMP creep**: torch defaults change; pin `torch.backends.cuda.matmul.
  allow_tf32=False` and no autocast — fp32 everywhere (mini-AGI §6.1: any shorter
  format rounds away most of an Adam step; fp16 destroys the moments).
- **Optimizer contract**: the custom inline update (not `torch.optim.AdamW`) is
  intentional — it reproduces the live numpy trajectory bit-for-bit. Do not
  "upgrade" it to a stock optimizer without a deliberate re-baseline.
- **Tail-credit divergence** is the silent-bug risk — parity test now compares
  the accumulators themselves (ring_b exact, ring_w / tail_E ~1e-06 rel).
- **Ring warmup after resume**: `ring_b`/`ring_w` are NOT persisted (numpy has
  the same omission; persisting them would change the checkpoint contract and
  ~3× its size). After a resume, cold-dim embed credit warms up over the first
  `ring_k` steps (≤18); tail E and decaytrace ARE persisted, so hot dims are
  exact immediately. Documented, not fixed.
- **Equal-step hub conflicts**: resolved in code — a pull with equal `t` and
  different content fails loudly; `--force` overrides. Sidecar hashes make the
  comparison exact.
- **`float(loss)` per step** forces a host sync (~0.1 ms, measured within the
  31 ms step); async logging is a possible later micro-optimization.
- **Colab eviction mid-push**: atomic tmp+rename on disk, Hub upload of the tmp
  name never happens — push only the `os.replace`d final name.
- **Checkpoint growth with B** (states/tail at B=4096 ≈ 170–300 MB): keep last-K
  tagged, prune old ones, bf16-moments shrink (§ below) only if sync becomes the
  bottleneck.
- **B=4096 on T4 is fine; B=8192 is not.** First GPU session runs `bench_gpu.py`
  with `nvidia-smi` before committing an experiment.
- **Auto-restart limits**: free Colab can't reliably auto-reconnect; a dead
  session costs ≤ its last checkpoint (≤ 10 min of work). Accept it; don't fight
  it.

## 7. From-scratch corpus arms (FS-W / FS-N / FS-L)

**Why from scratch, not continuation:** the live checkpoint (t=64,747) was
trained on TinyStories. A continuation A/B of "incumbent data vs novels" is
confounded — the incumbent arm is *more of what the model already knows*.
Starting each arm at t=0 from a bit-identical seeded init (`--seed 0`, default
`default_rng(0)`) makes the corpus the only axis that differs.

| arm | corpus | question |
|---|---|---|
| **FS-W** | `roneneldan/TinyStories` at a **+220 MB offset** (past the locally staged 165 MB, so it cannot overlap the ruler's decontaminated eval) | the incumbent's data, clean |
| **FS-N** | Gutenberg `fiction_books` (MIT) | does narrative prose grow long-memory dims? |
| **FS-L** | layered mix: Gutenberg + FineWeb-Edu (score>=3) + UltraChat | does multi-domain beat single-domain? |

**Budget:** one hour of GPU wall clock each. Training length is *derived from a
measured in-session rate*, not guessed: the bundle runs a 24-step calibration,
reads the B/s, then takes
`steps = min(train_budget_s * B/s / B, available_bytes * 0.87 / B)` so the run
fits BOTH the time and the data envelope. At the measured ~27.5 kB/s this is
~80k steps ≈ 1.25× the live checkpoint's entire history.

**Byte-matching:** same `--seed 0` (identical init), same `--data-seed 42` (same
file ordering), same B=1024, same ring_k=14, hence identical per-step cost.
Gated by `check_trainer` item 13.

```bash
.venv/bin/python make_fs_bundle.py                    # writes all three
colab run --gpu T4 --timeout 4200 colab_fs_w.py      # then n, then l
```

**Local smoke test (2 min, free, no GPU, no network):**
```bash
TMT_FS_SMOKE=1 TMT_FS_SMOKE_LOCAL=1 TMT_FS_BUDGET_S=400 .venv/bin/python colab_fs_w.py
```
SMOKE mode puts `HF_HUB_OFFLINE=1` and passes no `--hub-repo`, so a local run
**cannot** publish to the live checkpoint lineage. (It did once, before that
guard existed; the 18 toy tags were deleted and the repo now holds only
`tmt_t000042`, `tmt_t064747`, `tmt_t094747`.)

**Verdict:** `eval.py` 3-file mean ± SE against the **0.03 CE** bar, comparing
the three arms to each other (not to the incumbent — a t=0 run has 64,747 steps
of missing history, so an absolute comparison to the live model is not fair at
equal wall clock).
